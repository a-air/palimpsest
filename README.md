# 支援未来 · AI 记忆管理与储存架构

> `palimpsest` — 记忆精炼与奖励引擎：把长对话压成可审计的事实节点，用探针问答验真，用版本链处理"事实变了"。
> *[English](README.en.md)*
>
> *A memory refiner with probe-based verification and a fact version chain. No self-grading.*

---

## 为什么做这个

上下文压缩到处都有，但绝大多数只回答一个问题：**"压得够短吗"**。
真正要命的是另一个问题：**"压完之后，下一棒的它还答得对你今天说过的话吗"**。

这个项目把"记忆"当成可以考试的东西：

- 每次压缩都**留档**（原文 + 节点 + 元信息），一个字不删
- 分数**由脚本算**，模型只负责写，不负责评
- 事实冲突走**版本链**，旧的标 `superseded`，不覆盖、不删除
- 用**探针问答**做语义验收：从原文出题，只给节点作答，数答对几道

---

## 三层结构

```
宪章层 constitution   人格 / 铁律 / 关系 / 医疗基线   ← 永不压缩，只追加
事件层 facts.jsonl    原子事实：带出处、置信度、生效区间、版本链
原文层 archive/       每次压缩的原始文本，原样留存
```

**没有任何一档会被删除。** 精炼只决定"能不能直接注入"，不决定"留不留"。

## 快速开始

**先自检，不用配任何东西：**

```bash
python refiner.py doctor
```

它会告诉你 python 版本、key 从哪儿来（环境变量 / `config.json` / DSH 凭证 / WSL 配置）、归档里有多少东西。

> key 的查找顺序：环境变量 → 项目 `config.json` → `~/.dsh/.credentials.yaml` → WSL 里的 Hermes 配置。
> 都找不到也能用 `score` `recall` `facts` `history` `refine` `report`（全部离线）。
> 想固定下来就跑 `python refiner.py setup --from-dsh`，写进本地 `config.json`（已 gitignore）。

```bash
# 1. 压缩并归档（低于 800 字符会拒绝，因为压了会比原文更长）
python refiner.py compress --raw path/to/dialog.md --title "3 月交付"

# 2. 跑探针问答（多两次模型调用，但它才是真指标）
python refiner.py compress --raw path/to/dialog.md --probe

# 3. 只算分，不调模型（零成本，可反复跑）
python refiner.py score --raw dlg.md --node archive/2026-03-02/xxx_node.json

# 4. 外部裁判找茬（智谱 GLM 免费档，只列清单不打分）
python refiner.py judge --raw dlg.md --node node.json

# 5. 按主题召回活跃事实
python refiner.py recall --q "供应商 交付" --inject

# 6. 看一条事实的版本链
python refiner.py history --id 3f468a476dc7
```

## 三个硬伤，以及现在怎么处理

批评是这么来的，认了，也都改了：

**① 中文分词的天花板 → 不装了，改成"能分就分，不能分就闭嘴"**

`auto_terms()` 换成无监督新词发现：**凝固度（PMI）× 自由度（左右熵）**。
碎片的右邻字几乎固定（"供应商**那边**"），左右熵趋近 0，直接被淘汰。
**语料 < 3000 字时直接返回空**——几千字的样本上任何分词器都会吐碎片，与其污染召回，不如不用，
让召回落到"实体覆盖 + 符号匹配"上。`score()` 输出里的 `term_mode: off` 就是这个状态。

**② Bigram 读不懂同义改写 → 加了一层归一化**

`normalize()` 把说法拉齐：全角→半角、`2026-03-02`/`3-02`/`3月2日` 统一、`十八`→`18`、
`推迟/延迟/延期`→`延后`、`号`→`日`。
现在 `"交付日延迟到 18 号"` 与 `"推迟到 18 日"` 的支撑度是 **1.00**（以前约 0.2，会被判无支撑）。

**③ 落盘文件的数据地狱 → SQLite FTS5 索引**

```bash
python refiner.py index            # 归档全量灌进 state/memory.db（可重复跑）
python refiner.py search --q 供应商  # trigram 子串检索，不再遍历文件
```

**文件仍是唯一真相**，DB 只是加速层：删了随时重建。
trigram 对 2 字查询无能为力，会自动退回 LIKE。

## 上下文水位 · 滑动窗口 · 烂 JSON

**① 本地数 token，不靠猜**

`context` 命令先算清楚再决定要不要压：

```bash
python refiner.py context --raw dlg.md
# token 102300 ｜ 上限 128000 ｜ 安全水位 102400（80%）｜ 占比 79.9%
# => 已经过水位：立刻压缩
```

装了 `tiktoken` 就用真 tokenizer；没装走校准过的启发式（中文 ≈1.6 字/token），误差 ±15%，
但水位本来就留了 20% 余量，够用。**80% 就打断，剩下 20% 留给回复和打分。**

**② 滑动窗口，最近几轮不进压缩池**

```bash
python refiner.py compress --raw dlg.md --keep-turns 4
```

最近 4 轮原样留在 `_recent.md` 里（高精度上下文），更早的进压缩池。

**③ 烂 JSON 不再炸**

`repair_json()` 自己会修：代码围栏、前后废话、尾逗号、单引号键、没引号的键、`True/False/None`。
装了 `json_repair` 就用它兜底。再修不好就**二次打脸**：把报错和原输出一起丢回模型，
"你刚才输出的不是合法 JSON，立刻修好，只输出 JSON，不要解释。"

## 支援未来

这个项目注定会变笨重。

它不打算解决"数据地狱"——它就是要吞下这些数据。三千个文件夹、几十万条事实，
都是留给未来的原材料。今天的模型读不完；等上下文突破到千万级、甚至硬件再上一个台阶，
那时会有一个模型把它们一口气读进去，重新精炼成一个人。

所以这里有三个刻意的选择：

- **原文一个字不删**，哪怕它拖慢检索
- **元信息写得足够自解释**，未来不依赖本程序也能读懂
- **索引可丢弃可重建**，DB 只是加速层，不是真相

> 有些东西不可能完美地交给未来。
> 能做的，是别在交出去之前就把它弄丢了。

## 生命周期：热 → 封存 → 冷箱

平时**只读精炼后的节点**，不读封存的原文——这是上下文压力的主要来源。

```
压缩 → [热] 当前批次，随时可用
   ↓ seal（压缩前提醒一次，确认后封存）
[封存] 原文留着，但不参与日常读取
   ↓ 每 4 次封存解锁一次 review
[冷箱] 核验 ≥85 才打包；平时不读，index --cold 才收录
```

```bash
python refiner.py seal      # 提醒一次 → 封存当前批次
python refiner.py review    # 核验最近 4 份封存；平均 ≥85 且最低 ≥75 才进冷箱
python refiner.py cold      # 看冷箱里有什么
```

- 封存/冷箱都是**搬家不是删除**，原文一个字不少
- 核验不通过就留在封存态，下次再核
- 冷箱里的节点默认不进索引、不进召回——要读得显式要

## 命令

| 命令 | 作用 | 是否要模型 |
|---|---|---|
| `compress` | 摘要 → 节点 → 归档 → 并入事实库 | 要 |
| `score` | 只算分 | 不要 |
| `probe` | 探针问答（出题 + 作答 + 核对） | 要 |
| `judge` | 外部裁判列漏项 | 要（GLM） |
| `refine` | 每 4 次压缩做一次分层精炼 | 不要 |
| `recall` | 关键词召回活跃事实 | 不要 |
| `index` | 归档灌进 SQLite 索引 | 不要 |
| `search` | FTS5 子串检索 | 不要 |
| `context` | 看 token 占比、要不要压缩 | 不要 |
| `seal` | 封存当前批次（提醒一次） | 不要 |
| `review` | 核验 4 份封存，≥85 进冷箱 | 不要 |
| `cold` | 看冷箱 | 不要 |
| `facts` | 列出活跃事实 | 不要 |
| `history` | 看版本链 | 不要 |
| `rebuild` | 从 archive 重建事实库 | 可选 |
| `report` | 归档统计 | 不要 |

## 分数怎么算

```
score = 100 × F1(recall, precision) × ( 0.5 + 0.5×efficiency )

F1          = 2·R·P / (R+P)     ← 丢内容和编内容被绑在一起
recall      = 0.5×主题词 + 0.3×实体 + 0.2×符号（抽不出词时改权为 0.6/0.4）
precision   = 节点分句里能在原文找到支撑的比例（归一化后匹配）
efficiency  = min(1, 压缩率 / 0.70)   ← 只做乘数，不能拿来抵赖内容
```

**为什么从加权求和改成 F1**：加权求和时，"照抄原文不压缩"能拿 80 分，
"认真压缩"只有 75 分——结构错了。现在压得再狠，只要丢内容 F1 就掉，赚不回来。

三组实测：

| 输入 | 得分 |
|---|---|
| 空节点 | **0.0** |
| 原文照抄 | **50.0** |
| 认真压缩的样例 | **56.5** |

启用 `--probe` 后另给 `score_with_probe = 0.6×脚本分 + 0.4×探针分`。

### 探针判的是"答对"，不是"字出现过"

出题时模型必须**同时给出标准答案**（更新类必须是最终值，数量类必须是最终数），
判分比对答案：数字/日期要精确命中，且**不能多出别的日期**（多出 = 拿了旧版本）。
"3 月 12 日"答"3 月 18 日"的题 → 判错，哪怕原文里确实写过 3-12。

### 已知边界（必须写清楚）

- `recall` 是**代理指标**：便宜、稳定、可解释，但读不懂同义改写。
- **探针问答才是真指标**，但它要调两次模型。
- 所以：脚本分适合**横向比较**（同一天两个节点谁更好），不适合当绝对真理。

## 版本链

事实永不删除，只改状态：

```json
{
  "id": "1a38bb605af6",
  "text": "交付日已从 3-12 改为 3-18，第一批调整为 300 件。",
  "status": "active",
  "valid_from": "2026-10-20T10:00:00+08:00",
  "superseded_by": null
}
```

被覆盖的旧条目保留 `valid_to` 与 `superseded_by`，`history --id` 可以顺着链走回去。

**判定顺序**：先做确定性候选筛选（共享 4 字片段 或 相似度 ≥ 0.45），候选再交给模型判
`duplicate / update / contradiction`；**判不出来就两条都留着**——宁可不合并，也不乱覆盖。

降级模式（没有 API）只认一种覆盖：**共享片段 + 出现变化词**（已 / 离职 / 改成 / 不再 …）。

## 设计取舍

| 选择 | 原因 |
|---|---|
| 分数由脚本算，不让模型自评 | 同一个模型写+评，分数必然趋高 |
| 探针问答而不是"像不像" | 语义保真只能靠下游任务验证 |
| 事实不删只标 superseded | 记忆的价值在未来，删了就永远回不来 |
| 判不出关系就都留着 | 误覆盖比重复更贵 |
| 归档三件套（raw/node/meta） | 未来可以不依赖本程序直接读 |

## Roadmap

已经做完的（有实测数据，见 [docs/BENCHMARK.md](docs/BENCHMARK.md)）：

- [x] **SQLite FTS5 索引**：3000 节点实测 `search` 平均 1.5 ms
- [x] **上下文水位**：本地数 token，80% 触发压缩
- [x] **滑动窗口**：最近 N 轮原文不进压缩池
- [x] **生命周期状态机**：热 → 封存 → 核验 → 冷箱，带崩溃恢复与文件锁
- [x] **缺陷梯度校准**：Spearman ρ = 0.83（分数与质量强同向）
- [x] **联调**：compress / probe 真跑通过（judge 受免费额度限制）

还没做的：

- [ ] **人工标注校准集**（20 组）：把"ρ=0.83 对构造梯度"升级成"对真人判断"
- [ ] **增量索引**：现在 `index` 是 O(n)，3 万份要 80 秒，应按 mtime 跳过
- [ ] **embedding 检索**：智谱 embedding 目前限流，等额度；本地无 pip 装不了模型
- [ ] **全命令 `--json`**：方便被别的 agent 直接调用
