# 实测数据

> 所有数字都是本机跑出来的，脚本在 `scripts/`，可复现。

机器：Windows 11 / Python 3.11.15 / SQLite 3.53.1（FTS5 trigram）

---

## 一、规模验证（`scripts/bench_scale.py 3000`）

README 里立的目标是"三千个文件夹、几十万条事实"，这一栏是第一次真跑。

| 指标 | 数值 |
|---|---|
| 节点数 | 3000 |
| 每节点事实数 | 8（共 24,000 条） |
| 生成耗时 | 11.5 s |
| `index` 总耗时 | 8.20 s（**366 节点/秒**） |
| 库大小 | 8.0 MB |
| `search`（trigram）平均 | **1.5 ms** |
| `search` 最慢 | 17.2 ms |
| `auto_terms` 20 万字语料 | 0.19 s |

**结论**：
- 检索不再是瓶颈——3000 份节点，平均 1.5 毫秒，跟全盘遍历不是一个量级。
- `index` 是 O(n) 的，8 秒/3000 份；**3 万份大约 80 秒**，可以接受但不适合每次启动都跑。
  后面要做增量索引（按 mtime 跳过）。
- 抽词 20 万字 0.19 秒，性能没问题；问题是**召回质量**（小语料下宁可不出词）。

## 二、联调（`scripts/integration_smoke.py`）

离线测试证明逻辑对；这一栏证明"模型真的返回了能解析的东西"。

```
① compress … OK：8 条事实，1 块，标题「陈默解决信号线故障并调整供应商交付方案」
   分数 54.5（召回 0.47 / 精确 1.0）
② probe … OK：探针 1.0（3/3 命中）
   ✅ 陈默在3月5日决定让哪家供应商承担第一批200件？ → 备选供应商
   ✅ 供应商把样品推迟到哪一天？ → 3月12日
   ✅ 3月8日供应商确认模具到货后，主供应商最终承担多少件？ → 300件
③ judge … SKIP：HTTP 429（智谱免费档限流）
```

**结论**：
- `compress` / `probe` 端到端可用，模型输出的 JSON 能进 `repair_json` 并被解析。
- 探针拿到**标准答案**后判分是准的（3/3，且答案确实是最终值不是旧值）。
- `judge` 受免费额度限制，属于可选的第三方裁判，挂了不影响主链路。

## 三、校准（`scripts/calibrate.py`）

拿同一个原文，造 6 个质量递减的节点，看分数是否同向。

| 变体 | 分数 | 召回 | 精确 | 压缩率 |
|---|---|---|---|---|
| 完整 | 72.3 | 0.70 | 1.00 | 0.53 |
| 丢 25% | 70.6 | 0.58 | 1.00 | 0.65 |
| 丢 50% | 51.9 | 0.35 | 1.00 | 0.75 |
| 丢 75% | 37.1 | 0.23 | 1.00 | 0.82 |
| 全编 | 0.0 | 0.00 | 0.00 | 0.97 |
| 照抄原文 | 50.0 | 1.00 | 1.00 | 0.00 |

**Spearman ρ = 0.829**（质量等级 vs 分数）

**结论**：
- 分数能正确排序：完整 > 丢一半 > 丢四分之三 > 全编。
- "照抄"排在中游（50.0）是**设计使然**：它忠实（F1=1）但零压缩，效率乘数把它压到一半。
  这是刻意的取舍——照抄不是好记忆。
- ρ=0.83 说明分数**可以横向比较**，但离"绝对分"还差人工标注。

**这一节的诚实说明**：这是"已知缺陷梯度"校准，不是人工标注。
它证明了分数的**单调性**，没证明它和人的主观判断一致。后者在 Roadmap 里。
